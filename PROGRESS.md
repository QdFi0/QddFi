# PROGRESS.md

Context reference for QddFi (household finance tracker). Read before making changes — durable architecture, known bugs, and operational gotchas only. This file does not track session-to-session status; check `git log` for current state.

## 1. Project overview

QddFi: household finance tracker (budgeting, transaction ledger, CPF contribution tracking, income tax estimate, insurance/loan tracking, a unified recurring-payments register, dashboards) for a couple to log together.

**Stack — single file, no build step:**
- `index.html` (~7,020 lines): all markup, styles, app code.
- React 18 + ReactDOM via `<script>` CDN (unpkg, production builds), no JSX — `React.createElement(...)`, aliased `rc(...)`.
- Recharts 2.12.0, SheetJS `xlsx`, also CDN `<script>`.
- Firebase v8 "classic" SDK (not v9+ — avoids ES-module loading issues from plain `<script>` tag).
- Firestore only backend, no server code. Offline persistence enabled (`enablePersistence`).
- Auth: Google Sign-in via Firebase Auth, gated by hardcoded `ALLOWED_EMAILS` (`eng.teck.93@gmail.com`, `siruchew@gmail.com`) — intentional personal/trial setup. Firestore security rules mirror the same allowlist, already use `{householdId}` as wildcard path.
- Hosting: GitHub Pages, repo `https://github.com/qdfi0/QddFi.git`, live at `https://qdfi0.github.io/QddFi/`.

**Firestore data model:**
- Household document ID is user-chosen/generated (join-code system, see §2) — not hardcoded.
- Per household doc: `records`, `ledgerStart`, `assumptions`, `budgets`, `contracts`, `policies`, `recurring`, `familyMembers`, `categories` (`{expense, income}`), `accounts` (`{liquidCash, investments, property}`), `openingBalances`, `dismissedHints`, `cpfSettings`, `taxSettings`.
- Transactions: separate subcollection `households/{id}/transactions`, one doc per transaction — enables concurrent writes from both household members without whole-document overwrite (`persistAll`) clobbering.

## 2. Architecture — locked decisions

**Ledger model:** double-entry-like, simplified for the user. `sealedRecords` = read-only historical months. `ledgerStart` = date from which months are **derived**, not stored: `deriveRecord()` replays every transaction dated in that month against a running balance. `computeBalances(registry, opening, txns, asOf)` — `registry` is a flattened list of every account (bank, investment, `cpfPerson1.oa/sa/ma`, `cpfPerson2.oa/sa/ma`, property/loan), each keyed like `liquidCash.bankAccount1`. New households bootstrap directly into the live ledger (`ledgerStart = today`, `sealedRecords: []`) — no backfill period.

**Household identity (join-code system):** `LEDGER_DOC`/`TXN_COL` are `let`, resolved at runtime by `resolveHousehold(name)` (index.html:95) — not hardcoded consts. Code stored in `localStorage["householdName"]`. Household creation: `generateHouseholdCode()` (index.html:89). Sanitization: `normalizeHouseholdName()` (index.html:83). Switching household = full page reload (avoids manual Firestore listener cleanup). No migration layer for the old hardcoded `households/etsy` doc — deliberately abandoned, don't build one without checking with the user first.

**Reset feature:** Settings → Household → "Reset household data" deletes the `transactions` subcollection and overwrites the household doc with `blankHouseholdDoc()` (single shared source of truth for a blank household).

**Key renames (fully migrated, flagging in case anything was missed):** `uob/dbsEtsy/dbsEt/syReserve`→`bankAccount1..4`, `endowusEt/endowusSy/moomooEt/moomooSy`→`investmentAccount1..4`, `cpfEt/cpfSy`→`cpfPerson1/cpfPerson2`, `payrollEt`→`primaryIncome`, `piano`→`secondaryIncome`, plus matching `cpfSettings`/`assumptions` field renames.

**Tab navigation (sidebar drawer):** Only `dashboard` and `daily` render as always-visible top-nav buttons (`PRIMARY_TABS`, declared just above `function App()`). Every other tab (`OTHER_TABS`: budgets, contracts, insurance, recurring, loans, cpf, tax, forecast, history, settings) lives behind a "☰ More" toggle (`sidebarOpen` state in `App`) that opens a fixed-position right-side drawer; clicking an item sets `tab` and closes the drawer. Adding a new secondary tab = append to `OTHER_TABS`, no other wiring needed. The `tab === "x" && ...` routing itself is unchanged — this was a nav-chrome-only change.

**Daily ledger quick-add (redesign shipped):** Account field is always a plain `<select>` (`AccountSelect`) — the old chip/pill quick-picks and "More…" toggle are gone. "Who" only renders when `type === "income"` (silently defaults to `"Joint"` otherwise) since CPF/tax attribution is the only thing that needs it. Categories can be pinned via a `pinned` boolean, set from Settings → Categories ("Pin to top" toggle next to Archive); pinned categories sort first in the ledger's category tile grid (`sortedCatList` in `TransactionsTab`). The From/To/Account/Search filter row collapses behind a "🔎 Filters" pill (`showFilters` state). The on-screen tap keypad (`.qty-keypad` CSS class) is hidden by media query on desktop/wide viewports (`@media (max-width: 640px), (pointer: coarse)`) since the Amount `<input>` already takes typed keyboard input directly — kept only for touch/mobile widths.

**Live balances (moved to Dashboard):** The account-balance breakdown + "Adjust" (reconcile) flow moved out of `TransactionsTab` into `App`'s dashboard render, as a "💰 Live balances · net $X" pill (`showLiveBalances` state) sitting above the Liquid cash KPI card. Expanding it shows the same grouped-by-account breakdown as before. `ReconcileDialog` is now driven from `App`-level state (`reconcileTarget`) rather than living inside `TransactionsTab`.

**Recurring items post real transactions (posting engine, shipped):** `recurring` items now carry `{type (expense/income/transfer), amount, account, toAccount, category, subcat, who, notes, interval, unit (day/week/month/year), nextDueDate, active, lastPostedDate}` instead of the old `{direction, frequency, dueMonth}` forecast-only shape. Stored as `recurringRaw` + `const recurring = useMemo(() => reconcileRecurring(recurringRaw), [recurringRaw])` — same raw/derived pattern as `categoriesRaw`/`categories`. `reconcileRecurring` (index.html, next to `FREQUENCIES`) migrates old-shape items and defaults `active: false` unless the item already has an account plus (category or toAccount) — nothing pre-existing started auto-posting the moment this shipped; it just sits "Incomplete" until reviewed. A `useEffect` in `App` (right after `reconcileAccount`) walks every active, complete item whose `nextDueDate <= today`, posts via `saveTxn` with a **deterministic id** (`` rec_<itemId>_<dueDate> ``) — two household members' browsers racing to post the same occurrence overwrite the same doc instead of duplicating — then advances `nextDueDate` with `addIntervalISO(cursor, interval, unit)`, looping to catch up on any missed occurrences. Self-limiting (no ref guard needed): once caught up, `nextDueDate` sits past today so the next pass is a no-op. The 12-month `forecast` useMemo precomputes a `recurByMonth` bucket by walking each active item's cadence forward from `nextDueDate` (replaced the old fixed calendar-month/frequency check), so the forecast and actual posting can never disagree. UI is `RecurringItemCard` (index.html, just before `TransactionsTab`) — same account/category/who fields as the daily ledger, plus "Every N day/week/month/year" and an editable next-due-date, with a status pill (Paused / Incomplete / Next: date).

**Insurance policies moved onto the same posting engine (shipped):** `policies` now carry the same cadence/posting fields as `recurring` (`amount, account, category, subcat, interval, unit, nextDueDate, active, lastPostedDate`) plus insurance-specific fields (`person, type, insurer, product, policyNumber, coverage, notes, lapseDate, locked`) — replacing the old forecast-only `{annualPremium, paymentFrequency, nextPaymentDate, paymentAccount (free text), paymentMethod}` shape, which never touched the ledger despite UI copy claiming otherwise. Stored as `policiesRaw` + `const policies = useMemo(() => reconcilePolicies(policiesRaw), [policiesRaw])`, same raw/derived pattern as `recurring`. Two small helpers shared by both migrations live next to `reconcileRecurring` (index.html): `legacyFrequencyToCadence(freq)` (old Monthly/Quarterly/Semi-Annual/Annual enums → `{interval, unit: "month"}`, one mapping instead of each migration hand-rolling its own) and `occurrencesPerYear(interval, unit)` (derives a per-occurrence `amount` from an old total-annual figure generically, no second hardcoded divisor table). `postDueCadence(item, today, saveTxn, buildTxn)` and `bucketDueAmounts(items, startKey)` (both next to `addIntervalISO`) factor out the "walk cadence forward, post/bucket every due occurrence" loop shared by the Recurring and Insurance posting effects and forecast calculations, so the two can't drift apart. A second `useEffect` in `App` (right after the recurring one) posts policy premiums as real `expense` transactions (id `` pol_<policyId>_<date> ``, `policyId` link field mirrors `recurringId`), capped so no occurrence posts past `lapseDate` — a lapsed policy stops charging premiums instead of posting forever. Same safety rule as the recurring migration: old policies' free-text `paymentAccount` can't be mapped to a real ledger account, so `active` only defaults `true` once a real `account`+`category` are already present — pre-existing policies sit "Incomplete" until reviewed, nothing silently starts auto-posting. Family coverage totals (Insurance tab) exclude lapsed policies (`lapseDate` in the past) — a lapsed policy provides zero actual coverage. No "mode of payment" field — the real ledger `account` being debited is the only source of truth for where a premium comes from. `AccountSelect`/`LedgerCategorySelect` gained a `disabled` prop (previously ignored) so the Insurance tab's pre-existing Save/Edit `locked` draft workflow disables every field consistently, including the two new selects.

**Loans tab: real posting, opt-in toggle, loan events (shipped):** `amortize()` (index.html) was rewritten from a fixed formula, `amortize(principal, ratePct, tenureYears)`, into `amortize(loan)` — one chronological month-by-month simulation over the loan's full history, so it can apply a chronological `events` list (new field on `housingLoan`/`carLoan`) in date order as it walks forward. Two event kinds cover early repayment, refinancing, and bank repricing with one mechanism (all three are mechanically "the schedule's terms reset as of this date," except a plain extra payment doesn't change the rate): `extraPayment` (`{date, amount}`) knocks the balance down immediately and lets the same payment keep being simulated — the loan just pays off sooner, achieving "shorten tenure" for free with no separate convention toggle; `rateChange` (`{date, ratePct, tenureYears (remaining), principal (optional override)}`) recomputes a fresh payment from the balance/rate/remaining-term as of that date — covers refinance and repricing identically. `amortize()` now also returns `monthly` (real calendar-dated month-by-month rows, not just `yearly` buckets) and `payoffDate` (the last simulated payment's date) alongside `payment`/`n`/`totalInterest`/`totalRepayment`/`yearly` as before. The Loans tab's "Scrollable view" toggle (`showMonthlySchedule`) previously only changed a scroll container around the same yearly table despite implying a monthly view existed — it now actually switches the table to `activeAmort.monthly`.

Each loan also gained `trackAsRecurring` (opt-in, defaults `false` — e.g. a CPF-funded housing installment should stay off, since it's not a cash outflow), `account`/`category`/`subcat` (real ledger account/category, same `AccountSelect`/`LedgerCategorySelect` pattern as Insurance), and `nextDueDate`/`lastPostedDate`. Confirmed scope: a loan payment posts as one flat `expense` (principal+interest together, no liability-account entry) — the amortisation table's own Balance column is what shows the outstanding-loan trajectory, not a second ledger posting; the interest/principal split stays a visual-only breakdown. Cadence is fixed at 1 month (not user-editable like Recurring/Insurance) since the amortisation math itself assumes exactly monthly compounding. A `useEffect` in `App` (right after the policy one) posts via the shared `postDueCadence`, capped at `amort.payoffDate` so a fully repaid loan self-stops; the same effect also walks `events`, posting any due-but-unposted `extraPayment` exactly once (guarded by an `event.posted` flag) as its own one-off transaction. `bucketDueAmounts` (shared with Insurance) feeds each loan's current payment into the Forecast the same way, also capped at `payoffDate`. `addLoanEvent`/`updateLoanEvent`/`removeLoanEvent` (near `addPolicy`) manage the events list; no lock/save step for events, unlike policies — they're deliberate, infrequent one-off entries. Old stored loans (pre-dating these fields) are backfilled via `{...blankLoan(), ...p.housingLoan}` at load time rather than a `reconcile*` migration function, since a loan is a single object, not an array needing per-item migration. The "Loan events" card is collapsed by default (`showLoanEvents` state, same show/hide-chip pattern as the daily ledger's "🔎 Filters") — early repayment/refinancing is ad hoc, so it stays out of the way until opened.

**Contracts tab removed, folded into Recurring (shipped):** the Contracts register (`name, provider, contractNumber, category, monthlyAmount, renewalDate, renewalFrequency, notes`) was the last forecast-only, never-posts-to-the-ledger register in the app — pressure-tested and confirmed genuinely redundant with Recurring (`name`/`provider`/`contractNumber` → Recurring's free-text `notes`; `monthlyAmount` → `amount` with fixed `interval:1, unit:"month"`; `category` already pulled from the same `categories.expense` list). `Recurring` items gained a general, first-class **`lapseDate`** ("End date" in the UI) — same field name/semantics Insurance policies already had, already understood by the existing generic `postDueCadence`/`bucketDueAmounts` helpers with zero changes needed to either. `RecurringItemCard` shows an "Ends in N days"/"Ended" flag (`daysUntil`, same ≤30/≤60 color thresholds Contracts used to show); the posting `useEffect` and the forecast's inline `recurByMonth` cadence walk both cap at `lapseDate` the same way Insurance/Loans already cap at `lapseDate`/`payoffDate`. **Important semantic change, deliberate**: Contracts' old `renewalDate` was a perpetual *reminder* (`nextOccurrence()` rolled it forward forever; the Forecast billed `monthlyAmount` every month regardless of "renewal") — never a stop signal. Recurring's new `lapseDate` is a genuine hard stop. Existing `contracts` are migrated at Firestore-load time (not via a `reconcile*` useMemo, since this is a one-time cross-register fold, not a per-item shape fix): each contract becomes a `recurring` item with a deterministic `contract_<id>` id (so the merge is idempotent across reloads), composed `notes` (provider/contract number/old renewal info/original notes joined by " · "), and **`lapseDate` deliberately left blank** — backfilling it from the old `renewalDate` would make a migrated contract silently stop posting the moment this shipped, which is exactly the confusion the semantic change above is meant to avoid. Starts `active:false`/blank `account`, same safety rule as every other reconcile/migration in this app. The one-time migration write bypasses `persistAll` (which always does a full-document `.set()` off current React state, not yet settled this render) and instead merges directly onto the freshly-loaded Firestore snapshot: `LEDGER_DOC.set({...p, recurring: mergedRecurring, contracts: []})`. Dead code removed alongside: `CategorySelectField`, `nextOccurrence()`, `FREQUENCIES`, `PAYMENT_METHODS` (the latter two unused since well before this — `FREQUENCIES` only Contracts used; `PAYMENT_METHODS` had been dead since the Insurance rework earlier this session).

Income aggregation (`totalIncome = sum(record.income)` in `computeDerived`) was checked by inspection and is unaffected — it's a generic recursive sum over whatever income categories have values, not a hardcoded primary/secondary list.

**History tab: Monthly/Annual toggle with a variance column (shipped):** the History tab was a single "All months" table with every month as its own column and no comparison. Replaced with a `historyPeriod` toggle (`"monthly"`/`"annual"`, `index.html` App state). Annual mode aggregates `records` by calendar year via a new `aggregateAnnual(records, derivedByMonth)` helper (index.html, next to `deriveRecord`) — deliberately *not* a uniform sum: flow metrics (income/expenses/net cashflow) sum across the year's months, but balance-sheet metrics (liquid cash, investments, CPF, net worth, buffer %) take the year's latest month that actually `hasBalances` (a point-in-time snapshot, since summing twelve month-end balances is meaningless) — `records` arrive pre-sorted chronologically so the last `hasBalances` month seen per year is that year's most recent by construction. Returns the same field shape as `computeDerived`'s output, so both views render through one shared `HISTORY_ROWS` row-definition array (`[label, raw-value getter, formatter]` — split from the old formatted-string getter specifically so the variance column has a real number to subtract) instead of duplicating the table per period type. The current calendar year's column is suffixed "(YTD)" since it's necessarily a partial-year sum. A variance column (`Δ vs last month` / `Δ vs last year`) is always shown, diffing the two most recent periods' raw values and formatting through a new `fmtDelta(raw, formatter)` helper (next to `fmtPct`) — reuses the row's own formatter with an explicit "+" prefix on positive deltas (fmt/fmtPct already render negative via their own "-" sign).

Monthly mode does *not* reuse `records` for its column list (initial version did, then was corrected) — `records` for a live household only spans `ledgerStart` to today (often just the current month for a freshly-bootstrapped household, since there's no backfill period), so the table was showing a single column. Monthly now always spans January of the current calendar year through the latest month regardless of what `records`/`derivedByMonth` actually cover — months with no derived record render as DASH in every cell rather than being omitted. The variance comparison is deliberately decoupled from this visible range (looked up straight from `derivedByMonth` by calendar month via `monthSortKey`/`monthLabelFromSortKey`, not from the rendered period array) so "vs last month" still reads correctly in January, when the previous month falls in the prior year and off the displayed columns. Verified the `aggregateAnnual` math directly (JavaScriptCore, since this Mac has no Node) against 14 months of synthetic data spanning two years — annual sums, point-in-time balance snapshots, partial-year YTD income, and both variance calculations all matched hand-computed expected values exactly — and verified the Monthly Jan-to-date column range and always-present variance column live in the browser.

**Backdated transactions silently dropped from every month-based view (fixed):** reported as "History doesn't show a backdated July entry" — root cause is upstream of History, in the `records` useMemo (index.html) that both History and Budgets/the Dashboard net-worth chart read from. `records` only derives months from `ledgerStart` (fixed once at household creation/reset, e.g. "Aug 2026" — it never moves backward on its own) through today; a transaction dated earlier than `ledgerStart` falls in a month `deriveRecord` never visits. Its balance-sheet effect still reached every later month's running balance (`computeBalances` has no date floor, so live balances/Dashboard KPIs looked correct), but its income/expense was never attributed to *any* month's P&L — silently missing from History, Budgets' trailing-3-month baseline, and the Net savings chart, while the transaction itself still listed correctly in the Daily ledger's raw transaction list (which reads `txns` directly, unrelated to `records`). Fixed by widening the derive range to the earliest transaction actually present (`Math.min` over `txns` dates vs. `ledgerStart`), capped to 120 months so one fat-fingered date can't force a runaway derive loop. Verified live: seeded a `2026-07-15` expense against a household with `ledgerStart` pinned at `2026-08-01` (the real bootstrap default) — before the fix, July was entirely blank (dashes) and August's own totals showed $0 expenses despite Live Balances correctly reflecting the transaction; after the fix, July shows the $250 expense with correct net cashflow/liquid cash/net worth, and August's variance column correctly diffs against it.

**Forward-proofed against month/year rollover (pressure-tested, minor cleanup shipped):** requested after the backdating fix above — simulate the app being used into next month and into a new year, confirm nothing breaks. 1. **Real syntax check via macOS's built-in JavaScriptCore** — authoritative (a real JS parser), not a heuristic. Run after any structural edit (adding/removing/replacing nested `React.createElement(...)`/`rc(...)` blocks), before even opening a browser:
   ```bash
   osascript -l JavaScript -e '
   ObjC.import("Foundation");
   function run(argv) {
     const nsstr = $.NSString.stringWithContentsOfFileEncodingError(argv[0], $.NSUTF8StringEncoding, null);
     const script = nsstr.js.split("<script>").pop().split("</script>")[0];
     try { new Function(script); return "OK"; } catch (e) { return "ERROR: " + e.toString(); }
   }' /Users/ethan/Documents/QddFi/index.html
   ```
   This only tells you *whether* it parses, not *where* the bug is — bisecting by truncating to N lines doesn't reliably localize it either, since a truncation inside still-valid nested structure always reports the same benign "Unexpected end of script" regardless of whether a real bug exists later in the file. What actually works: take the exact text you replaced (`git show <sha>:index.html`) and your new text, and compare their net open/close counts per bracket type (string-literal-aware, e.g. a small Python scanner) — for a like-for-like replacement they must match exactly, since everything outside the edited region is unchanged. This is exactly how a real bug got found in the recurring-tab session: one extra `)` in a JSX replacement, invisible to eye review, that only surfaced as a confusing "Unexpected token ')'" at the very end of the file.
2. **Bracket-balance heuristic (quick, noisy, use only as a first pass)**: Python script scans the last `<script>` block, treats `"`/`'`/`` ` ``-delimited spans as opaque, sums `( { [` vs `) } ]`. Compare against the same scan on the last known-good commit — should roughly match, but this scanner has known false positives (regex literals get misread as string delimiters) and the mismatch count can shift with unrelated edits even when the code is valid. Don't trust it alone — step 1 above is the real authority.
3. **Temporary `debug.html` inside the project folder** (`cp index.html debug.html`), skip auth by changing the final render line from `ReactDOM.createRoot(...).render(React.createElement(LoginGate, null, React.createElement(App, null)))` to `ReactDOM.createRoot(...).render(React.createElement(App, null))` (Firebase Auth requires http/https, won't work over `file://`).
